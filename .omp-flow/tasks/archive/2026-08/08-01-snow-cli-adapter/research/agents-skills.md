# Snow agents, Skills, and native identity

This investigation answers whether pinned Snow CLI can consume omp-flow's shared Skills and
whether its native agent/task surfaces can preserve the required exact
`native item id = actorId` correlation. It uses the task-local
[Snow upstream Reference](../reference/snow-cli-upstream.md), pinned to
`MayDay-wpf/snow-cli@86a18cfbf5844c14a99dcc717eed26b8cf5b89d4` (Snow `0.8.24`,
2026-07-31), plus the repository's current mechanical contract. No implementation was performed.

## Decision summary

- **Shared Skills are directly usable.** Snow scans project and global `.agents/skills` as an
  explicit compatibility surface. A second managed `.snow/skills` copy is unnecessary and would
  introduce shadowing ambiguity.
- **Snow does not use a singular `.agent` root for sub-agent definitions.** It recursively scans
  project `.snow/agents/**/*.md` and global `~/.snow/agents/**/*.md`, in addition to
  `~/.snow/sub-agents.json` and built-ins.
- **A Snow agent definition ID is not a native execution ID.** Direct sub-agent instances are
  keyed by the model/provider tool-call ID; nested instances, Team member IDs, Team task IDs, and
  background task IDs are generated by Snow. Multiple executions may share one definition
  `agentId`.
- **Consequently, current Snow cannot satisfy omp-flow's exact dispatch binding through its
  standard sub-agent, Team, or background-task surfaces.** Naming-grammar preflight alone cannot
  repair a surface whose unique execution ID is not caller-controlled before the assignment is
  dispatched.
- **Pinned 0.8.24 also has a project-agent exposure gap.** The docs say arbitrary Markdown agents
  are schedulable, but the native tool catalog includes only built-ins and JSON-configured user
  agents. Project/global Markdown agents reach discovery and resolution, but a new custom ID is
  not registered as a callable `subagent-*` tool. A project Markdown override of an existing
  built-in ID does work.

These findings **confirm** the anchor's thin-adapter and ownership boundary, but **revise** the
assumption that a Snow-native executor can be added once its ID grammar is known. The missing
capability is caller control/reservation of a unique native execution ID, not merely character
validation. This is consequential enough to return to Brainstorm before design.

## Agent definitions and precedence

Snow's Markdown loader recursively accepts `.md` files, derives `id` from frontmatter or the
filename stem, derives `name` from frontmatter or `id`, accepts `description`, accepts a scalar or
array `tools`, and uses the body as `role` when frontmatter `role` is absent
(`.omp-flow/cache/repos/snow-cli/source/utils/config/projectAgents.ts:13`,
`.omp-flow/cache/repos/snow-cli/source/utils/config/projectAgents.ts:53`,
`.omp-flow/cache/repos/snow-cli/source/utils/config/projectAgents.ts:60`). The only local ID check
is non-emptiness; there is no character, length, or uniqueness validation
(`.omp-flow/cache/repos/snow-cli/source/utils/config/projectAgents.ts:75`). The pinned tests
explicitly accept `trellis-implement` and default `my-agent` from a hyphenated filename
(`.omp-flow/cache/repos/snow-cli/source/test/projectAgents.test.ts:14`,
`.omp-flow/cache/repos/snow-cli/source/test/projectAgents.test.ts:47`). See the pinned
[loader](https://github.com/MayDay-wpf/snow-cli/blob/86a18cfbf5844c14a99dcc717eed26b8cf5b89d4/source/utils/config/projectAgents.ts#L13-L120)
and [tests](https://github.com/MayDay-wpf/snow-cli/blob/86a18cfbf5844c14a99dcc717eed26b8cf5b89d4/source/test/projectAgents.test.ts#L14-L69).

The actual definition roots are project `<cwd>/.snow/agents`, global `~/.snow/agents`, user-global
`~/.snow/sub-agents.json`, and built-ins. Merge priority is:

```text
project .snow/agents > global ~/.snow/agents > ~/.snow/sub-agents.json > builtin
```

This is a last-write-by-ID `Map`, so a higher-priority definition replaces a lower one
(`.omp-flow/cache/repos/snow-cli/source/utils/config/subAgentConfig.ts:72`,
`.omp-flow/cache/repos/snow-cli/source/utils/config/subAgentConfig.ts:77`). Snow does not scan
`.agent`, `.agents/agents`, or existing Codex/Claude/OMP native agent roots. `ROLE-<agentName>.md`
at the project root or `~/.snow` is a separate project-over-global prompt overlay keyed by agent
**name**; it does not register an agent ID
(`.omp-flow/cache/repos/snow-cli/source/utils/commands/roleSubagent.ts:21`,
`.omp-flow/cache/repos/snow-cli/source/utils/commands/roleSubagent.ts:151`). The upstream format and
precedence are also documented in the pinned
[Sub-Agent guide](https://github.com/MayDay-wpf/snow-cli/blob/86a18cfbf5844c14a99dcc717eed26b8cf5b89d4/docs/usage/en/05.Sub-Agent%20Configuration.md#L103-L148).

### Counter-evidence: discovery is not reliable custom dispatch

`getSubAgents()` merges all four definition sources and the picker displays that effective list
(`.omp-flow/cache/repos/snow-cli/source/utils/config/subAgentConfig.ts:77`,
`.omp-flow/cache/repos/snow-cli/source/hooks/picker/useAgentPicker.ts:15`). Resolution by a known
ID also uses the merged list, which is why the test proves a project definition can override
`agent_explore` (`.omp-flow/cache/repos/snow-cli/source/utils/execution/subAgentResolver.ts:9`,
`.omp-flow/cache/repos/snow-cli/source/test/projectAgents.test.ts:126`).

However, the callable tool catalog uses `getUserSubAgents()`, which reads only
`~/.snow/sub-agents.json`, then adds the hard-coded built-ins
(`.omp-flow/cache/repos/snow-cli/source/mcp/subagent.ts:93`,
`.omp-flow/cache/repos/snow-cli/source/mcp/subagent.ts:101`,
`.omp-flow/cache/repos/snow-cli/source/mcp/subagent.ts:204`). The MCP manager wraps only that list
as `subagent-${tool.name}`
(`.omp-flow/cache/repos/snow-cli/source/utils/execution/mcpToolsManager.ts:452`). Thus a new
project/global Markdown custom ID may appear in the picker but is absent from the model's
registered tool schema. This contradicts the guide's unqualified “schedulable” claim. The feature
landed in commit
[dfd35d1c](https://github.com/MayDay-wpf/snow-cli/commit/dfd35d1c1836fa3fca7c80b96575e23476021656)
without changing `source/mcp/subagent.ts`; there is no pinned test for custom Markdown tool
registration. Compatibility design must treat arbitrary project-agent dispatch as unproven/broken
until upstream closes this gap or an end-to-end released build proves otherwise.

## Native identity taxonomy

Snow has several IDs with different owners. Treating them as interchangeable would create false
correlation.

| Surface | Caller-controlled label | Unique execution/task ID | Evidence and implication |
|---|---|---|---|
| Direct sub-agent | Definition `agentId`; Markdown permits a non-empty string and examples use hyphens | `instanceId = toolCall.id`, generated before Snow's executor receives the call | The running tracker is keyed by instance ID and explicitly allows multiple instances for one `agentId`; definition ID is a type, not an execution identity (`.omp-flow/cache/repos/snow-cli/source/utils/execution/toolExecutor.ts:395`, `.omp-flow/cache/repos/snow-cli/source/utils/execution/toolExecutor.ts:411`, `.omp-flow/cache/repos/snow-cli/source/utils/execution/runningSubAgentTracker.ts:21`, `.omp-flow/cache/repos/snow-cli/source/utils/execution/runningSubAgentTracker.ts:329`). |
| Nested sub-agent | Requested `agent_id` | `spawn-${Date.now()}-${random}` | Snow generates and registers it internally; caller cannot supply it (`.omp-flow/cache/repos/snow-cli/source/utils/execution/subAgentToolInterceptor.ts:347`). |
| Team teammate | `name`, accepted after a worktree sanitization check | `member.id = randomUUID().slice(0, 8)` and `instanceId = member.id` | The name selects the worktree but is not native identity (`.omp-flow/cache/repos/snow-cli/source/utils/team/teamConfig.ts:111`, `.omp-flow/cache/repos/snow-cli/source/mcp/team.ts:308`). |
| Team shared-list task | Title/description/assignee | `randomUUID().slice(0, 8)` | `create_task` returns the ID only after creation (`.omp-flow/cache/repos/snow-cli/source/utils/team/teamTaskList.ts:62`, `.omp-flow/cache/repos/snow-cli/source/mcp/team.ts:578`). |
| Background AI task | Prompt passed to `snow --task` | Full `randomUUID()` | Snow creates the record, immediately spawns the child, then prints the ID (`.omp-flow/cache/repos/snow-cli/source/utils/task/taskManager.ts:83`, `.omp-flow/cache/repos/snow-cli/source/cli.tsx:619`). |

Pinned anchors: [direct instance registration](https://github.com/MayDay-wpf/snow-cli/blob/86a18cfbf5844c14a99dcc717eed26b8cf5b89d4/source/utils/execution/toolExecutor.ts#L394-L460),
[running identity model](https://github.com/MayDay-wpf/snow-cli/blob/86a18cfbf5844c14a99dcc717eed26b8cf5b89d4/source/utils/execution/runningSubAgentTracker.ts#L21-L53),
[nested instance generation](https://github.com/MayDay-wpf/snow-cli/blob/86a18cfbf5844c14a99dcc717eed26b8cf5b89d4/source/utils/execution/subAgentToolInterceptor.ts#L285-L380),
[Team member generation](https://github.com/MayDay-wpf/snow-cli/blob/86a18cfbf5844c14a99dcc717eed26b8cf5b89d4/source/utils/team/teamConfig.ts#L111-L136),
[Team task generation](https://github.com/MayDay-wpf/snow-cli/blob/86a18cfbf5844c14a99dcc717eed26b8cf5b89d4/source/utils/team/teamTaskList.ts#L62-L87), and
[background task generation](https://github.com/MayDay-wpf/snow-cli/blob/86a18cfbf5844c14a99dcc717eed26b8cf5b89d4/source/utils/task/taskManager.ts#L79-L101).

Team `name` behavior deserves a separate warning. Snow normalizes NFKC, replaces characters other
than Unicode letters/numbers/`_`/`-` with `_`, collapses underscores, trims them, and lowercases
the result for `.snow/worktrees/<team>/<member>` and branch
`snow-team/<team>/<member>` (`.omp-flow/cache/repos/snow-cli/source/utils/team/teamWorktree.ts:8`,
`.omp-flow/cache/repos/snow-cli/source/utils/team/teamWorktree.ts:32`,
`.omp-flow/cache/repos/snow-cli/source/utils/team/teamWorktree.ts:41`). The config nevertheless
stores the original name and a random member ID. `addMember` does not reject duplicate names, and
`createTeamWorktree` returns an existing path if present, so a teammate name is especially unsafe
as unique mechanical identity. See the pinned
[worktree implementation](https://github.com/MayDay-wpf/snow-cli/blob/86a18cfbf5844c14a99dcc717eed26b8cf5b89d4/source/utils/team/teamWorktree.ts#L6-L59).

## Concurrency and result delivery

Direct sub-agent calls are ordinary independent tool calls. Snow groups tools by resource and
runs different groups with `Promise.all`; sub-agent calls fall into unique independent groups
because no special serialization is defined
(`.omp-flow/cache/repos/snow-cli/source/utils/execution/toolExecutor.ts:734`,
`.omp-flow/cache/repos/snow-cli/source/utils/execution/toolExecutor.ts:831`,
`.omp-flow/cache/repos/snow-cli/source/utils/execution/toolExecutor.ts:840`). No width cap was found.
The parent awaits each direct sub-agent's result and returns `result`, usage, injected messages,
and termination instructions as the tool result
(`.omp-flow/cache/repos/snow-cli/source/mcp/subagent.ts:67`). Multiple same-type instances are
explicitly modeled and precise messaging requires `instanceId`
(`.omp-flow/cache/repos/snow-cli/source/utils/execution/runningSubAgentTracker.ts:329`).

Nested spawning is asynchronous and width-uncapped, but its depth is controlled by project/global
`subAgentMaxSpawnDepth`, default `1`
(`.omp-flow/cache/repos/snow-cli/source/utils/config/projectSettings.ts:39`,
`.omp-flow/cache/repos/snow-cli/source/utils/config/projectSettings.ts:87`,
`.omp-flow/cache/repos/snow-cli/source/utils/execution/subAgentBuiltinTools.ts:94`). Completed nested
results are buffered in the main-process tracker for later delivery; this is not a stable external
task receipt (`.omp-flow/cache/repos/snow-cli/source/utils/execution/runningSubAgentTracker.ts:34`,
`.omp-flow/cache/repos/snow-cli/source/utils/execution/subAgentToolInterceptor.ts:382`).

Team spawns are fire-and-forget child processes with per-member worktrees; results are stored by
random member/instance ID, while a separate random-ID shared task list coordinates work
(`.omp-flow/cache/repos/snow-cli/source/mcp/team.ts:286`,
`.omp-flow/cache/repos/snow-cli/source/mcp/team.ts:329`,
`.omp-flow/cache/repos/snow-cli/source/mcp/team.ts:350`). The guide calls this true parallelism and
recommends 3–5 teammates but says there is no theoretical limit
([Team guide](https://github.com/MayDay-wpf/snow-cli/blob/86a18cfbf5844c14a99dcc717eed26b8cf5b89d4/docs/usage/en/22.Team%20Mode%20Guide.md#L519-L535)); no enforcement cap was found.

Background tasks spawn detached child processes, pass the generated UUID through
`SNOW_TASK_ID`, and persist state under `~/.snow/tasks`
(`.omp-flow/cache/repos/snow-cli/source/utils/task/taskExecutor.ts:69`,
`.omp-flow/cache/repos/snow-cli/source/utils/task/taskExecutor.ts:76`,
`.omp-flow/cache/repos/snow-cli/source/utils/task/taskManager.ts:40`). The user-facing `--task`
surface accepts only a prompt and prints the generated ID after the child has already been
started; `--task-execute` is the internal child path
(`.omp-flow/cache/repos/snow-cli/source/cli.tsx:346`,
`.omp-flow/cache/repos/snow-cli/source/cli.tsx:619`,
`.omp-flow/cache/repos/snow-cli/source/cli.tsx:650`). It therefore cannot reserve an arbitrary
omp-flow actor ID and then accept the operation-produced assignment.

## Skills compatibility and precedence

Snow recursively discovers directories containing exact-case `SKILL.md`. The skill ID is the
normalized path relative to the Skills root; nested IDs use `/`. It parses YAML `name`,
`description`, and comma-separated or array `allowed-tools`, ignores unknown metadata, and retains
the Markdown body (`.omp-flow/cache/repos/snow-cli/source/mcp/skills.ts:28`,
`.omp-flow/cache/repos/snow-cli/source/mcp/skills.ts:93`,
`.omp-flow/cache/repos/snow-cli/source/mcp/skills.ts:97`). This is compatible with omp-flow's
existing common Skill layout under `.agents/skills`.

The implemented low-to-high precedence is:

```text
bundled
< ~/.agents/skills
< ~/.snow/skills
< <project>/.agents/skills
< <project>/.snow/skills
```

Later loads replace the same relative skill ID
(`.omp-flow/cache/repos/snow-cli/source/mcp/skills.ts:178`,
`.omp-flow/cache/repos/snow-cli/source/mcp/skills.ts:194`,
`.omp-flow/cache/repos/snow-cli/source/mcp/skills.ts:219`). See the pinned
[Skills loader](https://github.com/MayDay-wpf/snow-cli/blob/86a18cfbf5844c14a99dcc717eed26b8cf5b89d4/source/mcp/skills.ts#L178-L243).
The user guide is stale here: it lists only `.snow` roots, despite implementation support for both
`.agents` roots. The implementation and commit
[abc78f37](https://github.com/MayDay-wpf/snow-cli/commit/abc78f37c41abc9a521a5fc9c48e6c9f702f8d02)
are the stronger evidence.

Two caveats remain:

1. A project `.snow/skills/<id>` silently shadows the same managed
   `.agents/skills/<id>`. Installation/update verification should surface this effective-source
   conflict; it should not create another owned copy to win precedence.
2. `allowed-tools` becomes prompt-level `<tool-restrictions>` text when the skill is executed
   (`.omp-flow/cache/repos/snow-cli/source/mcp/skills.ts:401`,
   `.omp-flow/cache/repos/snow-cli/source/mcp/skills.ts:439`). It is not evidence of an OS sandbox
   or a separate mechanical allowlist.

## Exact actor correlation against omp-flow

omp-flow requires `operation start` to be the sole producer of the exact native assignment and
requires the native item ID to equal its `actorId`; a mismatch must fail before the child starts
(`templates/.omp-flow/workflow.md:123`, `templates/.omp-flow/workflow.md:129`,
`templates/.omp-flow/workflow.md:134`). The existing OMP adapter enforces this equality and checks
the actor/receipt/path tuple against the active operation (`src/omp/extension.ts:240`,
`src/omp/extension.ts:256`, `src/omp/extension.ts:263`). The runtime itself deliberately validates
only a non-empty actor string and later exact equality; it does not own Harness grammars
(`templates/.omp-flow/scripts/common/operation_store.py:95`,
`templates/.omp-flow/scripts/common/operation_store.py:171`).

The mechanical ordering is therefore:

```text
choose legal native item ID
  -> operation start --actor-id <that exact ID>
  -> receive immutable assignment containing actorId + receipt
  -> dispatch native item with id=<same ID> and exact assignment
```

Snow's current standard surfaces cannot perform that sequence:

- `agentId` can be chosen first, but it identifies a reusable definition and may have several
  simultaneous `instanceId`s. Equating it with actor identity loses execution uniqueness.
- direct and nested `instanceId`s are generated by the provider/Snow after the model issues the
  tool call;
- Team member IDs and shared task IDs are generated inside their create calls;
- background task UUID is generated only after `snow --task <prompt>` has already received the
  prompt and the child is immediately started.

Post-hoc recording of a generated Snow ID as an external receipt would not repair the initial
actor/native-item mismatch. Pre-creating or editing Snow's global task JSON, using the internal
`--task-execute`, writing a custom dispatcher, or treating a teammate name as identity would cross
the thin-adapter boundary and still not establish the native contract.

The earlier `data-researcher`/`data_researcher` failure remains valid evidence that a caller-owned
native ID grammar must be checked **before** `operation start`. For Snow Markdown definition IDs,
however, the pinned code exposes no complete grammar beyond non-empty, even though hyphens are
demonstrably accepted; provider tool-name constraints can still be narrower. A conservative
character check may prevent some bad definitions, but it cannot produce a caller-owned unique
Snow execution ID. Harness-specific preflight belongs at the adapter/native-dispatch seam, not in
the portable Python operation store.

## Recommended decision and unresolved questions

Return to Brainstorm and choose explicitly between:

1. **Safe initial degradation:** install/reuse common `.agents/skills`, document Snow's native
   `.snow/agents` format where useful, and fail closed/declare unsupported for omp-flow native
   research/implementation/review dispatch. Do not claim agent execution correlation.
2. **Upstream capability first:** require Snow to expose a supported reserve/create API or CLI
   option that accepts a caller-supplied unique task/member/instance ID before receiving the exact
   assignment, and an observable completion/result receipt. Then a thin adapter can validate Snow's
   published ID grammar before `operation start` and forward the tuple unchanged.

Do not select “map actorId to agent definition ID/name” as a third path; the evidence falsifies its
uniqueness.

Open questions for upstream or a later bounded probe:

- Is the project/global Markdown custom-agent tool-registration gap intentional, or will Snow
  register `getSubAgents()` rather than only `getUserSubAgents()` in a released fix?
- What provider-independent tool-name grammar will Snow guarantee for custom agent IDs? The current
  loader accepts values that downstream model APIs may reject.
- Will Snow add caller-supplied IDs to background tasks or Team members/tasks, or a two-step
  reserve-then-execute contract?
- If such an API appears, what native completion/result event is stable enough to serve as the
  external receipt without parsing authored prompts or task Markdown?
