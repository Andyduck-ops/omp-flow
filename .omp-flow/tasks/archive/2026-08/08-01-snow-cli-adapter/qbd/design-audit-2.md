## Decision-critical assessment

No decision-critical blocker remains in the current design.

The strongest apparent blocker is Snow native operation dispatch. Pinned Snow 0.8.24 does not let
omp-flow choose the unique execution identity before submitting the assignment, and its callable
tool catalog does not reliably register arbitrary new project Markdown agent IDs. That would make
a claim of full Snow Execute/Review/QbD parity false. The current PRD and Design do not make that
claim: they require exact actor/native-item binding when available, prohibit aliases and post-hoc
receipt rewriting, and require an unsupported path to fail visibly. The remaining main-session
adapter still has independently usable Skills, session isolation, Hooks, installation, update, and
Flow Status surfaces. Removal or disabling of the unsupported native dispatch path therefore
prevents false correlation without defeating the whole selected outcome. Under the QbD threshold,
this is residual capability risk rather than a blocker.

The strongest Cursor uncertainty is whether `sessionStart.env` reaches every relevant terminal,
resume, and subagent path in the released product. The linked research records that no Cursor
runtime was available for capture. Failure of that bridge would make session-dependent operations
unavailable, but the portable resolver has no project-global fallback: absent an explicit context,
selection fails with the existing missing-session error. Consequently the unproven path does not
currently establish a data-mixing or false-authority consequence. Runtime capture remains required
before claiming support on those paths, but missing evidence does not justify `NEEDS_EVIDENCE` for
the bounded fail-closed design.

## Evidence, assumptions, and counter-evidence

### Confirmed evidence

- Snow reads project `.agents/skills`, so a duplicate `.snow/skills` tree is unnecessary. Snow
  exposes `SNOW_SESSION_ID`, which fits the portable runtime's existing mechanical session-key
  boundary. See [Snow agents and Skills](../research/agents-skills.md), [Snow Hooks](../research/hooks.md),
  and [adapter contract](../research/adapter-contract.md).
- Snow's agent-definition ID is a reusable type, while direct, nested, Team, and background
  execution IDs are generated by Snow/provider paths. The relevant pre/post Hooks omit the unique
  execution ID. Exact `native item ID = actorId` therefore cannot be represented on the pinned
  standard dispatch paths.
- A non-empty project `.snow/hooks/<event>.json` replaces the corresponding global event rules;
  it does not compose with them. Snow executes command Hooks through the platform shell, and some
  failure paths are explicitly best-effort or fail-open. Exact-owned managed files protect project
  destinations but do not prevent this global-rule shadowing consequence.
- Cursor's documented project surfaces match the proposed thin adapter: root `AGENTS.md`, project
  `.agents/skills`, `.cursor/agents`, and one `.cursor/hooks.json`. The linked [Cursor research](../research/cursor.md)
  also records the absence of a released-runtime smoke capture.
- The repository already centralizes Harness ordering/configuration, exact managed resources,
  hash-based update behavior, and `{{PYTHON_CMD}}` rendering in
  [`src/cli/harness.ts`](../../../../src/cli/harness.ts) and
  [`src/cli/init.ts`](../../../../src/cli/init.ts). The proposed additions use those seams rather
  than adding a second adapter framework.
- The portable resolver checks explicit context and supported Harness session variables, then
  returns no active task when none is present; it does not use a project-global selection fallback.
  See [`active_task.py`](../../../../templates/.omp-flow/scripts/common/active_task.py).

### Assumptions still carried by the design

- Snow command strings rendered with the selected Python executable work under both its POSIX
  shell and Windows `ComSpec` execution paths.
- Cursor's `sessionStart` output injects the context into the top-level agent shell for the
  supported release, and any unsupported resume/subagent path fails without ambient context.
- The universal `flow-status` Skill can select one explicit current host even when the project
  config contains multiple Harnesses; the Harness config alone is not a current-session signal.
- Native agent frontmatter accepted by static fixtures is sufficient for discovery. This does not
  prove that Snow can call a new project role or that either Harness can preserve strict operation
  identity.

### Strongest counter-evidence

- [Snow agents and Skills](../research/agents-skills.md) shows that arbitrary project Markdown
  Snow agents can be discoverable yet absent from the callable `subagent-*` tool catalog. Five
  installed operation-role cards may therefore be inert on the pinned release.
- [Snow Hooks](../research/hooks.md) shows that installing `onSessionStart.json` and
  `beforeToolCall.json` suppresses same-event global rules. The later user calibration selected
  project Hooks and rejected global merging, but it did not change the upstream precedence fact.
- Current Cursor reports corroborate that `sessionStart.env` reaches the top-level shell tool but
  can be absent [after reopening a conversation](https://forum.cursor.com/t/env-exported-in-sessionstart-hook-does-not-persist-across-cursor-restarts/157196)
  and [in subagents](https://forum.cursor.com/t/subagents-do-not-inherit-environment-variables/155212).
  These observations strengthen the linked research's requirement for a released-runtime gate;
  they do not change the safe failure result of the current portable resolver.

### Accepted scope decisions carried into this audit

- Global Hook merging/coordination is outside scope.
- Native operation dispatch is unsupported wherever exact actor/native identity cannot be
  preserved; no alias or post-hoc receipt is permitted.
- A duplicate Harness Skill tree, generalized identity framework, custom dispatcher, and authored
  Markdown state parser remain rejected.
- Real-platform Cursor capture and cross-platform Hook smoke testing are verification work, not
  evidence already claimed as complete.

## Advisory observations

These observations are non-blocking because each has an explicit safe degradation that preserves
the core install/session capability and prevents the material consequence.

1. **Snow role cards need a truthful capability boundary.** Cause: the Design lists five strict
   operation-role cards although pinned Snow may not register new project agent IDs and cannot
   provide exact execution identity. Consequence: installed files could imply a callable,
   receipt-safe path that does not exist. Decision: during decomposition, require each Snow card
   and README capability statement either to reject strict operation dispatch explicitly or omit
   the card until an end-to-end native identity proof exists. The safe degradation is removal of
   those cards; shared Skills and main-session operation commands remain available.

2. **Default Snow Hooks suppress global same-event rules.** Cause: Snow uses project-over-global
   fallback, not composition. Consequence: selecting `--snow` may disable unrelated user policy,
   orientation, or protection actions for `onSessionStart` and `beforeToolCall`. Decision: carry a
   visible init/README disclosure and a testable capability statement, or narrow the first release
   by omitting those event files. Exact project-file ownership alone is not disclosure. Omission is
   safe because `SNOW_SESSION_ID` and `.agents/skills` do not depend on Hooks.

3. **Cursor session verification must cover lifecycle boundaries, not only handler fixtures.**
   Cause: the Design relies on Hook-returned environment while Research lacks a released runtime,
   and known behavior differs for top-level, reopened, and subagent sessions. Consequence:
   top-level selection may work while resumed or delegated work gets a missing context. Decision:
   make a released-runtime check prove top-level shell injection, two concurrent conversations,
   reopen/resume, and subagent behavior; record unsupported cases as visible unavailability. A
   fixture proving two payload IDs hash differently is necessary but not sufficient to claim native
   lifecycle support.

4. **Use the documented Cursor identity field explicitly.** The PRD and linked research name
   `conversation_id`, while the Design prose switches to `session_id`. The handler should require
   the documented `conversation_id` for its supported contract and treat any `session_id` alias as
   versioned compatibility input, with fixtures preventing silent empty or mismatched selection.

5. **Define host selection for combined installs.** Updating the universal `flow-status` Skill to
   “choose the current Harness” is not executable guidance when config contains Snow and Cursor
   together. Decomposition should bind host choice to concrete runtime evidence such as
   `SNOW_SESSION_ID` or injected `OMP_FLOW_HOST`, fail on ambiguity, and test every existing and new
   host. It must not select from Harness config order.

## Residual risk

The principal residual risk is capability overstatement rather than silent mechanical corruption:
Snow cards may be installed but not callable, Cursor context may disappear on a lifecycle path,
and Snow project Hooks have a user-visible global precedence effect. The Design's exact-identity
failure rule, absence of a project-global active-task fallback, and existing managed-file conflict
behavior contain those failures. Human calibration should decide whether the remaining usability
and Hook-precedence costs are acceptable for decomposition.
