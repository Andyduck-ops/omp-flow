# B-A001--001 — Simplify Skill deployment and protect project Wiki ownership

## Objective

After A-001 establishes the one-file Skill and project Wiki, remove the nested-Skill deployment
machinery and make init/update preserve `.omp-flow/wiki/` as project-owned data.

## Approved requirements

- PRD R3 and the control-plane portions of R5.
- PRD AC2–AC5 and AC7.
- Design sections 1, 2, 5, error behavior, migration, and verification.

## Dependency

Requires completed `A-001` because managed registration must resolve the new
`templates/common/skills/omp-flow-wiki/SKILL.md` and the old source tree must already be retired.

## Scope

In scope:

- `src/cli/init.ts`
- `src/cli/update.ts`
- exact obsolete-resource disposition needed for previously managed
  `omp-flow-verifiable-claims` files
- both tracked `templates/.omp-flow/scripts/common/disposition.py` and
  `.omp-flow/scripts/common/disposition.py` only where stale store wording/membership changes
- `tests/omp-flow.test.ts`
- affected generated fixtures whose executable output changes
- package and scratch project verification

Out of scope:

- editing Wiki Concept substance
- adding assets/references to other Skills
- a generic managed-directory abstraction
- Wiki schema/content tests or exact Concept-count assertions
- broader task Reference changes

## Inputs and bindings

- `project-wiki-ownership` defines seed-once and never-managed behavior.
- `wiki-skill-interface` defines one declared `SKILL.md` per registered Skill and retirement of
  the recursive walker/cache.

## Implementation contract

1. Replace `omp-flow-verifiable-claims` with `omp-flow-wiki` in the Skill registry.
2. Construct managed Skill resources as `SKILL_NAMES × selected Harness roots × SKILL.md`.
3. Remove recursive discovery, its cache, test reset export, and generic nested-tree fixture tests.
4. Preserve the existing explicit missing-required-resource failure for each declared Skill file.
5. After managed init deployment, create a minimal `.omp-flow/wiki/index.md` only if absent. Do
   not return it as a managed plan entry or write it to managed hashes; `force` must not alter it.
6. Replace retired `.omp-flow/specs/` and `.omp-flow/knowhow/` protected prefixes with
   `.omp-flow/wiki/`.
7. Use the existing obsolete-resource mechanism for the finite set of previously managed old
   Skill files. Do not install an alias or generic compatibility layer.
8. Keep tests focused on deployment and ownership behavior, not authored Wiki structure.

## Done conditions

1. Managed-resource enumeration contains one `SKILL.md` per registered Skill per selected Harness
   and no nested Skill payload.
2. Init in a scratch project seeds a missing Wiki root index.
3. Repeated init and forced init preserve a user sentinel in the existing index byte-for-byte and
   do not add Wiki paths to managed hashes.
4. Force update also preserves the Wiki sentinel.
5. The update protected-prefix list names `.omp-flow/wiki/` and no longer names the retired global
   stores.
6. Previously managed old Skill paths have deterministic obsolete disposition.
7. Recursive discovery/cache code and tests are gone; no hypothetical replacement abstraction is
   added.
8. Template/runtime control-plane copies remain aligned where both are tracked.

## Verification

Run and record:

```text
python -X utf8 -m compileall -q templates/.omp-flow/scripts
npm run build
npm test
npm pack --dry-run
git diff --check
```

Run the AGENTS.md scratch init smoke for the configured Harnesses. Inspect the scratch managed hash
file to confirm it has no `.omp-flow/wiki/` entry, mutate the root index with a unique sentinel,
then prove repeated/forced init and forced update preserve it.

## Handoff

Report changed files, deleted recursive seams/tests, the finite old-path retirement behavior,
commands and results, scratch preservation evidence, and any generated fixture changes. Call out
any deviation from the one-file managed Skill contract.
