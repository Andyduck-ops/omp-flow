# A-001 — Create the single project Wiki and Wiki operating Skill

## Objective

Establish `.omp-flow/wiki/` as this project's only durable knowledge store. Replace the
knowledge-bearing `omp-flow-verifiable-claims` Skill with a concise `omp-flow-wiki` procedure that
explains when Wiki use is appropriate, how to bootstrap and progressively distill knowledge for a
forked project with no Wiki, the maintenance philosophy, and how to consult and maintain Concepts.

This row owns authored Wiki and Skill content. It does not change init/update resource mechanics or
add permanent content-schema tests; those belong to `B-A001--001`.

## Approved requirements

- PRD R1, R2, R4, and the guidance portions of R5.
- PRD AC1, AC2, and AC6.
- Design sections 3–5 and the data-flow boundary.
- Human QbD 1 calibration: the Skill contains only operating rules, including appropriate-use
  guidance, methodology/philosophy, and update/maintenance procedure. Concrete knowledge lives
  only under `.omp-flow/wiki/`.
- Human QbD 2 calibration: because work commonly begins from a fork with no Wiki, the operating
  rules must also cover minimal bootstrap and evidence-led knowledge distillation without bulk
  speculative documentation.

## Skill content contract

The Skill must explain:

1. **When to use the Wiki:** consult it when durable project knowledge may change a decision; update
   it when an evidenced lesson is reusable beyond the current task.
2. **Bootstrap when absent:** when `.omp-flow/wiki/index.md` is missing, establish only a minimal
   entry point. Do not attempt an up-front summary of the whole repository or manufacture a
   complete taxonomy.
3. **Distill progressively:** while investigating or working, identify durable candidates from
   authoritative code, tests, project documentation, build/configuration behavior, history, and
   observed failures. Confirm each claim with the strongest evidence reasonably available before
   persisting it; do not impose an arbitrary source count.
4. **Fork provenance:** distinguish upstream project facts from fork-local behavior and divergence
   when that distinction affects future decisions. Record useful paths, revisions, or upstream
   anchors as optional provenance rather than mandatory fields.
5. **Methodology:** one project truth, progressive disclosure, durable/reusable/evidenced content,
   proportional verification, and no persistence for temporary or speculative observations.
6. **Maintenance:** start at `.omp-flow/wiki/index.md` or a known Concept; add, revise, merge
   duplication, index,
   deprecate, and preserve useful history; retain unknown OKF frontmatter; keep optional fields
   optional.
7. **Boundary:** no project Concept or knowledge payload belongs inside the Skill itself.

It must not make the model follow a fixed topic taxonomy or mechanically choose every navigation
or verification decision. Bootstrap and distillation are incremental operations, not a mandate to
scan and document the entire repository.

## Done conditions

1. The three agreed Concepts exist once under `.omp-flow/wiki/`; the two migrated bodies preserve
   their substantive claims.
2. The evidence-led exploration Concept captures the approved philosophy: investigation precedes
   design, evidence is accumulated before synthesis, context should not be fragmented
   unnecessarily, and rigor stays proportional to the decision.
3. The root index gives useful progressive navigation without claiming exhaustive membership.
4. The shared and configured `omp-flow-wiki/SKILL.md` files are procedure-only and byte-identical.
   Their procedure covers consult, absent-Wiki bootstrap, progressive distillation, fork/upstream
   distinction, add/update/merge/index/deprecate maintenance, and boundaries.
5. No live `omp-flow-verifiable-claims` Skill directory remains in the template or configured
   Harness roots.
6. Live brainstorm, research, finish, and workflow guidance invokes `omp-flow-wiki`.
7. No parser, link-closure rule, fixed Concept body schema, or permanent exact Concept-count test
   is added.
